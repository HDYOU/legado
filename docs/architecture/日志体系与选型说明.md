# 日志体系与选型说明

> 适用范围：Legado Max 项目内所有"打日志"的入口——它们分别流向 logcat、落盘文件、应用内日志页 / 调试悬浮球，彼此独立。想搞清楚"这行日志会出现在哪、该用哪个"时读本文。
> 有效状态：**有效**（以 `app/src/main/java/io/legado/app/` 下 `utils/LogUtils.kt`、`utils/DebugLog.kt`、`utils/log/TimberLog.kt`、`constant/AppLog.kt`、`model/Debug.kt` 当前代码为准）。
> 定位：模块级技术笔记，与 [`Web服务端到端测试方法.md`](./Web服务端到端测试方法.md)、[`adb免点击验证数据驱动功能.md`](./adb免点击验证数据驱动功能.md) 平级；分组索引见 [README.md](./README.md)。

## 一、全景速览

项目里当前共存 **5 个日志入口**，其中 4 个是"后端 / 通道"，1 个是"聚合分发层"：

| 入口（类）                              | 底层机制                                                      | 最终去向                                                                                                                     | 开关 / 门控                                 | 初始化                    | 业务调用量                         |
| --------------------------------------- | ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- | ------------------------- | ---------------------------------- |
| `android.util.Log`                      | JNI → `liblog` → **logd** 守护进程                            | **logcat**（内存环形缓冲区）                                                                                                 | 无（平台自带，release 也输出）              | —                         | 少量直接 + 被封装                  |
| `DebugLog`（`utils/DebugLog.kt`）       | 转发 `android.util.Log`                                       | **logcat**                                                                                                                   | 仅 `BuildConfig.DEBUG` 生效，release 空操作 | —                         | 约 66 处                           |
| `LogUtils`（`utils/LogUtils.kt`）       | `java.util.logging` + `FileHandler`                           | **落盘文件** `externalCacheDir/logs/appLog-*.txt`                                                                            | 用户设置 `AppConfig.recordLog`              | `App.kt` `LogUtils.init`  | 约 118 处                          |
| `TimberLog`（`utils/log/TimberLog.kt`） | JakeWharton **Timber 5.0.1**（`implementation(libs.timber)`） | debug 下 `Timber.DebugTree()` → **logcat**（自动以调用类名为 tag）                                                           | 仅 `isDebuggable` 时 `plant`                | `App.kt` `TimberLog.init` | **仅 init，业务 0 处**（见第四节） |
| `AppLog`（`constant/AppLog.kt`）        | **聚合分发层**，非独立后端                                    | ① 应用内"日志"页 ② `LogUtils` 落盘 ③ debug 下 `android.util.Log` → logcat ④ `DebugEventCenter`（调试悬浮球 / HTTP 调试面板） | `AppConfig.recordLog` + `debugLogOnly*`     | —                         | 约 490 处（业务主入口）            |

> 一句话：**想在 logcat 看 → `android.util.Log` / `DebugLog`；想存成可导出文件 → `LogUtils`；业务运行日志统一走 → `AppLog`；`TimberLog` 目前形同虚设。**

## 二、`android.util.Log` 为什么会打到 logcat

`Log.d()` 自己不打印，只是把记录交给系统日志服务，`logcat` 是另一端的读者：

```
Log.d(tag,msg) ──JNI──► __android_log_print()  ──写 socket /dev/socket/logdw──►  logd 守护进程
                                                                              │ 存入按 buffer 分类的内存环形缓冲
adb logcat ──读 socket /dev/socket/logdr───────────────────────────────────────┘
```

- 记录含 优先级(V/D/I/W/E) + pid/tid + tag + msg，写入是异步、近乎零成本。
- logd 按 `main`/`system`/`crash`/`events`/`kernel` 分缓冲区存**内存**（滚动，非文件）。
- `logcat` 只是客户端，`logcat -d` 一次性 dump 后退出（免点击验证脚本用的就是它）。
- 过滤在读取端做（filter spec），源头还可用 `Log.isLoggable` + 系统属性 `log.tag.XXX` 关闭高频日志。

## 三、各入口详解与使用范围

### `DebugLog` — 纯开发期 logcat 快捷方式

`e/d/i/w` 全部包在 `if (BuildConfig.DEBUG)` 里，release 直接空操作，适合临时排查、不想污染 release 输出的场景。**去向只有 logcat，不落盘。**

### `LogUtils` — 用户可导出的持久化文件日志

基于 `java.util.logging`，只挂了一个 `AsyncFileHandler` 把日志写进 `externalCacheDir/logs/appLog-*.txt`，保留 7 天后自动清理；是否落盘由**用户设置** `AppConfig.recordLog` 决定（关=Level.OFF）。**它不调用 `android.util.Log`，默认不进 logcat。** 适合"需要用户在 App 里复现、导出给我们看的长期日志"。

### `TimberLog` — 引进但尚未接入

`App.kt` 里 `TimberLog.init(this, isDebuggable)` 会在 debug 下 `plant(Timber.DebugTree())`（输出到 logcat，tag 自动取调用类）。但：

- 全项目对 `Timber` 的裸用为 **0**，对 `TimberLog.d/e/...` 的业务调用为 **0**——即"框架引进来了，除了 init 之外没有任何实际调用"。
- 其"带 TAG"那组方法（`d(tag,msg)` 等）其实**绕过 Timber 直调 `android.util.Log`**，与 Timber 无关，命名易误导。
- `CrashReportingTree` 只是示例占位（生产环境上报），**并未 plant**。

结论：把它当作"预备的统一日志门面"看待即可，现阶段不要依赖它做实际输出；要么后续全面迁移到 `TimberLog.*`（去掉 tag 版），要么移除依赖以免与 `LogUtils`/`AppLog` 三套并存造成困惑。

### `AppLog` — 业务日志主入口（四路分发）

`put / putSource / putNotSave / putDebug / putReaderDebug` 是**分发型**入口，一次调用可能同时：

1. 写入内存环形列表（`AppLog.logs` / `sourceLogs`，供应用内"日志"页展示，上限 100 / 200 条）；
2. 经 `LogUtils.d` 落盘；
3. debug 下用 `android.util.Log.e(调用类名, msg, throwable)` 打 logcat；
4. 通过 `DebugEventCenter.emit(DebugEvent(...))` 送到**调试悬浮球 / HTTP 调试面板**。

`putReaderDebug` 特殊：只发悬浮球、绝不写常规日志（阅读调试信息与全局日志隔离）。`shouldRouteToDebugOnly(category)` 命中时（`AppConfig.debugLogOnlyEnabled` + 类别匹配）跳过 1~3，只走悬浮球。

## 四、选型建议（该用哪个）

- **业务运行日志 / 错误、需要在 App 内日志页或调试悬浮球看到** → `AppLog.put*`（事实上的主入口）。
- **临时开发排查、只要 logcat、不进 release** → `DebugLog` 或直接 `android.util.Log`。
- **需要落盘、用户能导出复现** → `LogUtils`（受 `recordLog` 开关）。
- **书源 / JS 解析调试输出** → `model/Debug.kt`（debug 下 `Log.d("sourceDebug", …)` → logcat，同时喂给书源调试页 UI）；这是免点击验证脚本抓 `sourceDebug` 的依据。
- **`TimberLog`** → 除非决定全面统一日志门面，否则暂不新增调用（见第三节）。

## 五、已知坑 / 注意事项

- **别把 `LogUtils.d` 当 `android.util.Log.d`**：前者落盘、不进 logcat；用 `adb logcat` 抓不到它，要去缓存目录的 `appLog-*.txt` 看。
- **`TimberLog` 带 tag 的方法名不副实**：走的是 `android.util.Log`，不是 Timber。
- 五套通道彼此独立，排查"日志去哪了"时先确定用的是哪个入口，再对应去 logcat / 文件 / App 日志页 / 调试悬浮球 找。
